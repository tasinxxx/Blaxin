# Stonic Capability Matrix — BLAXIN Phase B Audit

**Method.** Every Stonic row cites Stonic's own public pages (stonicai.com, fetched 2026-09-15).
Every BLAXIN row cites real source locations and pinned tests. Source-code existence alone is
**not** treated as proof: where only unit tests (not real runtime runs) back a capability, the
status says so explicitly. No cloning — BLAXIN is an independent implementation.

**Status vocabulary:** MATCHED (implemented + verified at the Stonic floor) · SUPERIOR (beyond the
Stonic floor) · PARTIAL (real but narrower than Stonic's claim) · MISSING (no real implementation)
· UNVERIFIED (implemented; honest verification blocked by this environment).

## 2. Uncertain / unknown Stonic capabilities (not confirmed on their site)

Stonic is closed-source; the following cannot be confirmed from public material and are tracked
as unknowns, not floors: on-device model identity ("Both AI models — a fast one… a heavy one" —
hosted, per their FAQ: "the AI runs on our servers"); actual screen-understanding depth (claimed
but never demonstrated with evidence — screenshots or transcript proof); computer-use loops
(claimed "sees and acts", no public demonstration of closed-loop pixel→action verification);
whether actions are verified at all (their transparency claim covers logging, not verification).
**BLAXIN therefore does NOT need parity against unproven claims — only against the confirmed
rows above.**

## 3. Phase B implementation from this audit

The single highest-value parity gap found: **screen awareness is half-real**. The screenshot tool
verifies real pixels, but `settleResult()` reduced every tool result to text, so the model could
never actually SEE the screen it was told to act on. Stonic's core claim (AI reads the screen and
acts) had no BLAXIN equivalent end-to-end.

Implemented this phase (independent implementation, no cloning):
1. `ChatMessage.images` (bounded array of `{ mimeType, base64 }`) on the uniform message type.
2. `settleResult` carries a **bounded** image from screenshot tool results (single screenshot per
   step, hard size cap, stripped from anything persisted via `budgetImages()`).
3. Provider mappers translate images per wire format:
   - OpenAI-compatible: `tool` result → `user` content parts (`image_url` data URL) — the format
     the OpenAI Chat Completions API requires for images after a tool call.
   - Anthropic: `tool_result` content blocks gain `image` source blocks (base64).
   - Gemini: `functionResponse` parts gain `inlineData` parts.
   - Ollama: `images` array on the tool message (Ollama's native multimodal format).
